# セキュリティ上のリスク・想定されるコントラクト攻撃

本プロジェクトの性質上、投資家からの出資、NFT による持分管理、利益分配（ERC20）などが絡むため、以下の点を特に注意する必要があります。

---

## 1. 一般的なスマートコントラクト攻撃リスク

### 1.1 Reentrancy（再入可能性）攻撃

**評価メモ**: 独自トークン・USDTのため問題なし（※運用上の前提）

| 項目 | 内容 |
|------|------|
| **どこで起こる？** | 投資家への利益分配や元本返済などでユーザーに対してトークンを送る際、`transfer` や `call` などで外部コントラクトを呼び出す処理があるとき。 |
| **なぜ危険？** | ERC20 の `transfer` は通常 `call` より安全だが、外部コントラクトを直接呼ぶ場面があれば再入可能性のリスクが生じる。コール先が再度同じ関数を呼び出し、状態を悪用できる可能性がある。 |
| **対策** | Solidity 0.8.x 以降は **check-effects-interactions** パターンを徹底し、状態更新を先に行い、その後に外部コールする。OpenZeppelin の **ReentrancyGuard** を活用する場合も多い。 |

---

### 1.2 Integer Over/Underflow（整数オーバーフロー / アンダーフロー）

| 項目 | 内容 |
|------|------|
| **どこで起こる？** | 投資割合の計算や利益分配のロジックで、ユーザーの出資額に応じた分配額を計算する際、`uint256` の乗算や加算が想定外に大きくなる可能性がある。 |
| **なぜ危険？** | Solidity 0.8.x 以降は標準でオーバーフロー / アンダーフローを検出して revert するが、カスタムライブラリや低レベル演算を使っている場合は注意が必要。 |
| **対策** | なるべく標準の `uint256` 演算を使い、Solidity 0.8.x の安全策を活かす。設計段階で上限値（最大投資額、最大分配額など）を定義する。 |

---

### 1.3 Front-running（フロントラン）

**評価メモ**: タイミングは一定のため問題なし

| 項目 | 内容 |
|------|------|
| **どこで起こる？** | 特定の投資商品や利益分配を行うタイミングで、攻撃者が先回り（高いガス料金）でトランザクションを実行し、有利なポジションを取る可能性がある。 |
| **なぜ危険？** | レアな NFT を取得したり、分配直前に NFT を取得して利確するなどが挙げられる（分配の対象が「保有時点」ベースになっている場合）。 |
| **対策** | 分配対象を「特定のブロックナンバー」時点の保有者とするか、分配対象が確定した後の NFT 移転は分配を受けられないなどの仕組みを検討する。タイムロック機構である程度予測困難にする（完全には防げないが、攻撃の難度は上がる）。 |

---

### 1.4 Denial of Service（サービス拒否）

**評価メモ**: ガス代を考慮済みのため問題なし

| 項目 | 内容 |
|------|------|
| **どこで起こる？** | 大量の NFT 発行や利益分配を一度に実行すると、ガスが上限に達して処理が失敗する可能性がある。 |
| **なぜ危険？** | 大量のループ処理（全ユーザーに分配など）を 1 トランザクションで行うとガス制限超過のリスクがある。 |
| **対策** | 分配をバッチ処理やオフチェーンで対象者を計算し、段階的に複数回のトランザクションで分配する実装を検討する。Chainlink Automation などを使う場合でも、一度に大量の配列を処理しない仕組みが必要。 |

---

### 1.5 Access Control（権限管理）の欠陥

**評価メモ**: 設計済みのため問題なし

| 項目 | 内容 |
|------|------|
| **どこで起こる？** | 管理者のみが操作すべき関数に `onlyOwner` や `onlyAdmin` が抜けていると、第三者に不正操作される。 |
| **なぜ危険？** | 投資商品の登録や満期処理など、ビジネスロジックを根底から覆す操作をされる。 |
| **対策** | `Ownable` や `AccessControl` を適切に利用する。管理者アドレスをマルチシグ（Safe Multisig）にするなど、鍵管理を安全に行う。 |

---

### 1.6 Unchecked external call return values（外部コールの戻り値を未確認）

**評価メモ**: USDT のみなら問題なし？拡張を考え今のうちに対処するかどうか検討

| 項目 | 内容 |
|------|------|
| **どこで起こる？** | ERC20 の `transfer` は boolean を返すタイプが多いが、戻り値を無視していると失敗時に気づけない。 |
| **なぜ危険？** | 分配用トークンが正しく送金できないままコントラクトロジックだけ進行してしまう。 |
| **対策** | `require(token.transfer(...))` のように戻り値を必ずチェックする。 |

### 1.4 USDT ブラックリスト・Push 失敗による分配停止（F-2026-16871 対応済）

| 項目 | 内容 |
|------|------|
| **どこで起こる？** | `distributeYield` / `maturity` のループ内 USDT `transfer`。Tether ブラックリスト等で特定アドレスへの送金が revert または失敗する。 |
| **なぜ危険？** | 従来は 1 件の失敗でトランザクション全体が revert し、**全投資家の分配・満期が停止**し得た。 |
| **対策（実装）** | `UsdtTransferLib.tryTransfer`（low-level `call`、USDT の無戻り値対応）。失敗時は **`tokenId` エスクロー** + `YieldTransferFailed` / `PrincipalTransferFailed`。バッチカーソルは必ず進行。投資家は **`claimYield` / `claimPrincipal`**（`ownerOf` のみ）。BL 継続時は claim も失敗するが資金はコントラクト内に留保し、**他投資家・他商品は継続可能**。 |

**未請求リスク**: エスクロー残がある間、投資家が claim しないと資金がコントラクトに留まる。マイページは `*TransferFailed`（`recipient` indexed）+ `getUnclaimed*` / `getClaimableForToken` で案内（接続時 BL 判定は不要）。

### 1.4b Admin 配列 uint8 ループカウンタによる DoS（F-2026-16866 対応済）

| 項目 | 内容 |
|------|------|
| **どこで起こる？** | `_isWhiteLists()`、`initialize()`、`InvestmentNFT.setURI()` の admin 配列ループ。カウンタが `uint8` のため、admin 数が 256 以上で `i++` がオーバーフローし revert する。 |
| **なぜ危険？** | `_isWhiteLists` は deposit / withdraw / mintNFT / distributeYield / maturity / registerProduct 等の全主要操作のゲートであり、全ホワイトリスト関数が永続的に使用不能となる。 |
| **対策（実装）** | 全ループカウンタを `uint256` に統一。`addAdmin` に `MAX_ADMINS = 255` の上限チェックを追加し、配列の無制限肥大化を防止。 |

### 1.4c 投資家ゼロ商品による Automation 無限ループ（F-2026-16869 対応済）

| 項目 | 内容 |
|------|------|
| **どこで起こる？** | 投資家が一人も申し込まなかった商品（`raisedAmount == 0`）の `distributeYield` / `maturity`。NFT 未発行のため `getNFTInfos` が空配列を返し、ループが 0 回で終了する。 |
| **なぜ危険？** | `distributedCount` がインクリメントされないため、Chainlink Automation の `checkUpkeep` が同一商品を毎回返し、後続商品の自動処理が無期限にブロックされる。`maturity` も `BeforeDistributionCompleted` で永久に revert する。 |
| **対策（実装）** | `distributeYield` / `maturity` の先頭に `raisedAmount == 0` ガードを追加。投資家ゼロの場合は `distributedCount++` / `isMaturity = true` を即設定して早期リターン。yield 計算・NFT 外部呼び出しを完全にスキップ。 |
**Yield Sweep（F-2026-17209 対応）**: `maturity` および `claimPrincipal` は NFT burn 前に未請求 yield 全 slot を元本と合算して送金する。送金成功時は slot ごとに `YieldClaimed` を emit し burn。送金失敗時は元本もエスクローし burn しない。これにより「burn 後に yield が永久ロック」される状態を防止。

### 1.4d 資金補充後も Automation が再開しない（F-2026-16870 対応済）

| 項目 | 内容 |
|------|------|
| **どこで起こる？** | `distributeYield` / `maturity` が `productPool` 不足を検出し `isInsufficientBalance = true` を設定した後、管理者が `deposit` で資金を補充した場合。 |
| **なぜ危険？** | 従来の `deposit` は `productPool` を増加させるだけで `isInsufficientBalance` フラグをクリアしなかった。Automation の `checkUpkeep` はこのフラグが `true` のプロダクトを無条件でスキップするため、十分な資金があっても自動決済が再開せず、管理者が手動で `distributeYield` / `maturity` を呼ぶ必要があった。 |
| **対策（実装）** | `deposit` で `productPool += depositAmount` 直後に `isInsufficientBalance = false` を無条件クリア。次回の `distributeYield` / `maturity` でプールが依然不足していれば再度フラグが設定されるため、安全性は維持される。 |

### 1.4e 分配スケジュールの満期日超過による元本ロック（F-2026-16949 対応済）

| 項目 | 内容 |
|------|------|
| **どこで起こる？** | `registerProduct` で分配スケジュール（`distributionStartDate` + `distributionInterval` × (`totalDistributionCount` - 1)）が `maturityDate` を超えるパラメータが設定された場合。 |
| **なぜ危険？** | `maturity` は全分配完了を前提とするため、スケジュールが `maturityDate` を超えると開示された満期日に満期処理が実行できず、投資家元本が超過分の期間（月〜年単位）ロックされる。商品登録はワンショット操作で事後修正不可。 |
| **対策（実装）** | `registerProduct` に `DistributionDateLib.calculateNextDistributionDate` による最終分配日算出を追加。`lastDistributionDate > maturityDate` の場合 `InvalidMaturityDate` で revert し、不正なスケジュールの登録を防止。 |

### 1.4f 商品登録時の Tier Registry 未設定による投資不能（F-2026-16955 対応済）

| 項目 | 内容 |
|------|------|
| **どこで起こる？** | `registerProduct` で `requiredTier != 0` を指定したが、`allowedByTierAddress[requiredTier]` が空のまま商品が登録された場合（修正前）。 |
| **なぜ危険？** | `invest` / `mintNFT` は `hasPurchasePermission` で常に `false` となり、全投資家が `NotEligible` で拒否される一時 DoS。誤登録時は CREATE2 による NFT デプロイまで進みガス浪費も発生し得た。 |
| **対策（実装）** | `registerProduct` で `requiredTier != 0` かつ `allowedByTierAddress[requiredTier].length == 0` の場合 `TierNotConfigured` で revert。運用は Tier Registry 設定 → 商品登録の順を前提とする。 |
| **追補（実装）** | 誤った `requiredTier` が既に保存された場合は `SetTier.setProductRequiredTier` で商品単位に修正可能（非ゼロ tier は同様にレジストリ必須。満期済み商品も更新可）。`ProductRequiredTierUpdated` でオフチェーン開示。 |

### 1.4g initialize 時の admin 重複登録（F-2026-16872 対応済）

| 項目 | 内容 |
|------|------|
| **どこで起こる？** | デプロイ時の `Initialize.initialize(admins, ...)`。修正前は calldata 内の重複 admin を `push` でき、`addAdmin` だけが `AlreadyExistsAdmin` で拒否していた。 |
| **なぜ危険？** | `deleteAdmin` は先頭1件のみ削除するため、1回の削除で admin 権限が残りうる。`_isWhiteLists` の走査コスト増や `MAX_ADMINS` 枠の浪費。権限昇格には至らない Info レベル。 |
| **対策（実装）** | `initialize` のループで `j < i` の範囲の重複を `AlreadyExistsAdmin` で拒否。`addAdmin` と「admin 配列はユニーク」を統一。 |

## 2. 特殊な機能に関連したリスク

### 2.1 NFT 発行による持分管理

**評価メモ**: `safeMint` を使用しており、インクリメントで `tokenId` を管理しているため問題なし

**ダブルミント / 二重発行リスク**

- NFT を重複して発行してしまうバグや、`tokenIdCounter` が予期せず巻き戻されるバグなど。

**転売と分配**

- 分配権を持つ NFT が自由にトレード可能な場合、「分配時に持っている人」に利回りを与えるのか、「スナップショット時点で持っていた人」に与えるのか曖昧だとトラブルになる。

**対策**

- シンプルに `ERC721Enumerable` を使うか、`_safeMint` による ID 管理を明確にする。
- **分配対象の判定基準**をしっかり固める。

---

### 2.2 日本円入金とウォレット対応

**オフチェーン入金詐欺** — **評価メモ**: 問題なし（運用前提）

- 「銀行振込した」と言われたが実際は着金していないケース。管理者が誤って承認すると NFT を不当に発行するリスク。

**KYC / AML**

- 法的要件としてユーザー本人確認を行う必要がある。コントラクト自体というよりバックエンドとの連携だが、セキュリティの穴（ユーザー ID を偽装）が生じないか要注意。

---

### 2.3 満期処理

**評価メモ**: 満期処理の際に分配がすべて終わっているかのチェックを加える（`distributeYield` にもチェックを加える）

**強制的な NFT 焼却**

- `burn` 処理が実行されるタイミングを誤り、まだ分配が終わっていないのに NFT を焼却してしまうなどのロジックミス。

**元本返済額の算出**

- 投資額に対する返済額の計算式にバグがあると、過剰払い / 過少払いのリスク。
- 返済額の送金に失敗した場合のハンドリングも重要。

---

### 2.4 管理機能

**評価メモ**: コントラクトでチェックを実施しているため問題なし

**管理ダッシュボードへの依存**

- 万一、フロントエンドや管理ツールにバグがあり、誤った引数でコントラクト関数を呼び出す可能性がある。

**対策**

- コントラクトレベルで引数バリデーション（例: 投資商品 ID が存在するか、日付が過去日ではないかなど）をしっかり行う。

---

## 3. ERC20 トークンを使った利益分配

### 3.1 Token Contract のセキュリティ

**評価メモ**: USDT のため問題なし

- 分配に利用する ERC20 トークンがオーナー権限を持つ場合、発行・凍結などの操作が悪用されないかチェックする。
- トークンが不正に mint される可能性はないか。**NFT も問題なし（owner のみ）**。

---

### 3.2 手数料 / ガス不足

**評価メモ**: 配布する際の残高について再チェック

- 大量配布の際、コントラクトの ETH 残高不足（またはトークン残高不足）で失敗し、想定通り分配できない。
- 分配を複数トランザクションに分けて行うなどの設計を検討する。

---

### 3.3 Double claiming（二重請求）

**評価メモ**: 分配したかどうかはプロキシに情報を持っているため問題なし

- 分配情報がずさんな設計だと、同じ分配を何度も請求される可能性がある。
- 分配ロジックで「特定の分配 ID に対して、すでに受け取ったかどうか」を管理するなどの仕組みが必要。

---

## 4. その他の考慮

### 4.1 プライバシー / 規制面

- 投資家情報をオンチェーンで管理し過ぎるとプライバシー問題が起こる。
- KYC 情報や銀行振込に関する詳細はオフチェーン管理し、オンチェーンには必要最小限のみとする。

---

### 4.2 ソーシャルエンジニアリング

**評価メモ**: Safe（マルチシグ）を使用

- コントラクト固有の攻撃ではないが、管理者の秘密鍵やマルチシグのキーを悪用されると、全資産が抜かれるリスクがある。
- マルチシグを導入する、キー管理の徹底を行うなどセキュリティ意識が重要。

---

### 4.3 アップグレード / プロキシパターン

- 要件が変化しやすい投資プラットフォームでは、アップグレード可能なコントラクトを使う場合もある。
- 不注意なアップグレードが破壊的変更や管理者権限の漏洩を招かないよう、アップグレード手順と権限管理を厳重に行う。

**実装コントラクトの直接初期化防止（F-2026-17010 対応済）**: ERC-7546 / MC フレームワークのファンクションコントラクトはスタンドアロンでデプロイされるため、OpenZeppelin `Initializable` を継承する実装コントラクトは constructor で `_disableInitializers()` を呼び、外部からの直接 `initialize` 呼び出しを防止する。プロキシ経由の初期化には影響しない（delegatecall でプロキシ自身のストレージを使用するため）。

**initialize 時の admin 重複防止（F-2026-16872 対応済）**: `initialize` の `admins` calldata に重複がある場合 `AlreadyExistsAdmin` で revert し、運用時の `addAdmin` と同一の不変条件（admin 配列のユニーク性）を確保する。詳細は `docs/audit/fix/F-2026-16872-initialize-duplicate-admin-check.md`。

---

## まとめ

- 基本的なスマートコントラクト攻撃（Reentrancy、Overflow、Access Control 不備など）に加え、NFT の取引と分配で **フロントラン / タイミング攻撃**が起こり得る。
- 大量ループ処理（利益分配など）による **ガス上限超過リスク**にも注意が必要。バッチ実行やオフチェーン計算を検討する。
- **管理者アクセス**を厳格に制御し、マルチシグなどを利用することで、1 人の秘密鍵漏洩による重大被害を防ぐ。
- **満期処理、元本返済、NFT 焼却**といった重要なライフサイクルイベントは、厳重なバリデーションとトランザクション設計を行う。
- **KYC / AML** や銀行振込の連携部分はオフチェーン含めたセキュリティを考慮する。
- 最終的には、**セキュリティ監査と十分なテスト**を実施し、ユーザー資金を扱うという点を念頭に、堅牢なコントラクト設計を行うのが不可欠。
