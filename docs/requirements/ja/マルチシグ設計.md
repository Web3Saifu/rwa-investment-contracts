# マルチシグ設計要件（Safe）

---

## 1. 設計の目的

| 目的 | 説明 |
|------|------|
| **セキュリティの強化** | 単一の秘密鍵に依存しないことで、不正アクセスや鍵の紛失によるリスクを低減する。 |
| **共同管理の実現** | 複数の関係者による承認プロセスを導入し、組織的なガバナンスを強化する。 |
| **柔軟な資産管理** | トークン、NFT、スマートコントラクトの所有権を安全に管理する。 |

---

## 2. システム概要

1. **マルチシグウォレットの作成**  
   Safe を使用して、複数のオーナーと承認閾値を設定したウォレットを作成する。

2. **資産とコントラクトの管理**  
   ウォレットを通じて資産の引出しや、スマートコントラクトのアップグレードを管理する。

3. **承認プロセスのフロー**  
   トランザクション提案、承認、実行のプロセスを明確化する。

---

## 3. キーコンポーネント

### 3.1 オーナー（所有者）

| 項目 | 内容 |
|------|------|
| **役割** | ウォレットの管理者として、トランザクションの提案や承認を行う。 |
| **人数** | セキュリティと利便性を考慮して、最低 3 人以上を推奨。 |
| **鍵の管理** | 各オーナーは自分の秘密鍵を安全に保管し、可能であればハードウェアウォレットを使用する。 |

### 3.2 承認閾値

| 項目 | 内容 |
|------|------|
| **設定** | M-of-N の形式で、トランザクション実行に必要な最小承認数を設定する。 |
| **推奨値** | オーナー数に応じて、過半数（例: 3 人中 2 人）または全員一致など、組織のポリシーに合わせて決定する。 |

### 3.3 トランザクションフロー

1. **提案** — オーナーの一人がトランザクションを提案する。  
2. **通知** — 他のオーナーに提案が通知される。  
3. **承認** — 他のオーナーが内容を確認し、承認または拒否する。  
4. **実行** — 必要な承認数が集まったら、トランザクションを実行する。

### 3.4 資産とコントラクトの対象

| 種別 | 例 |
|------|-----|
| **ERC20 トークン** | ETH、USDT、独自のトークンなど。 |
| **ERC721 / 1155 トークン** | NFT やゲーム内アイテム。 |
| **スマートコントラクト** | アップグレード可能なコントラクトの管理権限。 |

---

## 4. 設計詳細

### 4.1 ウォレットの作成手順

**Safe インスタンスのデプロイ**

- Safe 公式ウェブアプリ（[https://safe.global/](https://safe.global/)）を使用して、新しいウォレットを作成する。  
- ネットワークの選択（Mainnet、Testnet など）。

**オーナーの追加**

- 各オーナーの Ethereum アドレスを入力する。  
- ハードウェアウォレットやセキュリティの高いウォレットを推奨する。

**承認閾値の設定**

- 組織のポリシーに基づき、トランザクション実行に必要な承認数を設定する。

### 4.2 資産の移行

**資産の送金**

- 既存のウォレットから Safe ウォレットに資産を送金する。

**コントラクトの所有権移行**

- スマートコントラクトのオーナーシップを Safe ウォレットのアドレスに変更する。

### 4.3 トランザクションの管理

| フェーズ | 内容 |
|----------|------|
| **トランザクションの提案** | オーナーが Safe のインターフェースから新しいトランザクションを作成する。 |
| **承認プロセス** | 他のオーナーに通知が送られ、インターフェース上で承認または拒否する。 |
| **実行** | 必要な承認数が集まると、トランザクションを実行可能になる。 |

### 4.4 アップグレード可能なコントラクトの管理

**アップグレード権限の移譲**

- コントラクトのアップグレード管理者を Safe ウォレットに設定する。

**アップグレード手順**

1. 新しい実装コントラクトのデプロイ  
2. アップグレード提案の作成  
3. プロキシコントラクトの実装アドレスを新しいものに変更するトランザクションを提案する  
4. 承認と実行 — オーナーの承認を得て、トランザクションを実行する  

---

## 5. セキュリティ考慮事項

### 5.1 鍵の管理（秘密鍵の保護）

- 各オーナーは秘密鍵を安全に保管する。  
- ハードウェアウォレットの使用やオフラインでのバックアップを推奨する。

### 5.2 オーナーの選定

| 観点 | 内容 |
|------|------|
| **信頼性** | オーナーには信頼できるメンバーを選定する。 |
| **多様性** | リスク分散のために、異なる場所や組織のメンバーを含める。 |

### 5.3 トランザクションの検証

| 観点 | 内容 |
|------|------|
| **内容の確認** | 各オーナーは提案されたトランザクションの内容を詳細に確認する。 |
| **ツールの活用** | トランザクションデータをデコードして表示するツールや、シミュレーション機能を利用する。 |

### 5.4 コントラクトの監査

| 観点 | 内容 |
|------|------|
| **事前の監査** | アップグレードするコントラクトのコードを第三者機関によるセキュリティ監査に付す。 |
| **定期的なレビュー** | コントラクトや運用プロセスを定期的に見直し、最新のセキュリティ基準に適合させる。 |

---

## 6. 運用とガバナンス

### 6.1 ガバナンスモデルの策定

- **意思決定プロセス** — トランザクションの提案から承認までの手順を明文化する。  
- **ポリシーの設定** — 資産の使用用途や上限額、緊急時の対応などのポリシーを策定する。

### 6.2 オーナーの追加・削除

- **プロセスの定義** — 新しいオーナーの追加や既存オーナーの削除手順を明確化する。  
- **承認の必要性** — オーナーの変更にもマルチシグの承認を必要とする設定とする。

### 6.3 緊急時対応

- **バックアップオーナー** — 万が一の事態に備え、バックアップのオーナーを設定する。  
- **緊急連絡手段** — オーナー間の迅速な連絡手段を確保する。

---

## 7. 実装ステップ

| 順序 | 内容 |
|------|------|
| 1 | **要件定義** — オーナー数、承認閾値、管理対象資産・コントラクトを明確化する。 |
| 2 | **Safe のセットアップ** — Safe ウォレットの作成とオーナー設定。 |
| 3 | **資産とコントラクトの移行** — 資産の送金とコントラクトのオーナーシップ移行。 |
| 4 | **テスト** — テストネットで運用フローを検証する。 |
| 5 | **セキュリティ監査** — 第三者による設定とプロセスの監査。 |
| 6 | **本番運用開始** — Mainnet での運用開始。 |

---

## 8. テストと検証

**テストネットでのシミュレーション**

- Ropsten や Goerli などのテストネットを使用して、全ての機能を検証する。

**シナリオテスト**

- 正常系・異常系のシナリオを用意し、各種ケースをテストする。

**ユーザートレーニング**

- オーナーとなるメンバーへの教育と操作訓練を行う。
